NOBAT-YAR


Frontend Specification for the
Remaining Pages
Handoff document for the programmer. It covers every page that is not built yet, with user flows, form rules, data models,
export and print requirements, and acceptance checks. Visual styling is out of scope: reuse the existing design system,
header, footer, cards and tokens. The homepage is already built.

How to read this document
 - This cover section and the sections GLOBAL 2, GLOBAL 3 and GLOBAL 4 are global: rules, routes, shared behavior and
   data. They apply to every page.
 - After that, each site page starts on its own PDF page (some run to two PDF pages).
 - Every site page follows the same structure: purpose, entry points, content, behavior, flows, edge cases, acceptance
   checks.
 - All user-facing text must be in Persian. Explanations here are English; Persian copy is kept in separate tables so the two
   never mix. Every piece of Persian copy is written out in real Persian script in tables titled Persian copy (shared copy is in
   GLOBAL 5). Use those strings exactly; for anything not listed, write natural, polite Persian in the same tone.


1. Project summary
 - Nobat-Yar is a Persian-language doctor appointment platform that covers several cities. It is not a single clinic.
 - Front-end only. No backend. All data is mock data plus browser storage.
 - It is a practice and portfolio project, not for real use. Its main showcase is form work: a one-time patient profile form, a
    short per-visit form, a clean profile table with PDF and Excel export, and a printable appointment sheet.
 - Status: the homepage is built. This document specifies everything else.


2. Technical baseline
 - React with Radix UI (already in the project). A Persian (Jalali) date picker is mandatory.
 - Right-to-left layout and the font already set in the design system.
 - Data: src/data/mock.js plus browser storage (see GLOBAL 3). No API calls.
 - No checkboxes anywhere. Allowed controls: RadioGroup, Select, Switch, ToggleGroup (single or multiple), Slider,
   Textarea, text and number inputs, and the Jalali date picker.
 - Review each page at desktop width and at 360 px mobile width before calling it done. Breakpoints: 1024 and 768.


3. Language and formats
Item                       Display in the UI                                           Stored
Digits                     Persian digits everywhere (labels, numbers, times, codes)   Latin digits
Dates                      Jalali, with month name in long form                        ISO Gregorian string (YYYY-MM-DD)
Time                       24-hour HH:mm in Persian digits                             HH:mm in Latin digits
Typing digits              Accept Persian and Arabic digits in every input             Normalize to Latin before validation and saving
Phone numbers              Persian digits, format 09xxxxxxxxx                          Latin string



4. Out of scope (do not build)
 - Real login, registration or authentication. Payments. SMS or email. Backend or admin tools.
 - Settings page: the menu item may exist but must be disabled or show a short coming-soon hint.
 - All-specialties page. Full province and city database (the city list stays Tehran and Karaj only).
 - Dark mode. Users writing new reviews (reviews are read-only sample data).

Flow A: first booking (new user)
    1. Landing or Doctors list: user opens a doctor card. The card button opens the Doctor page; it does not start booking.
    2. On the Doctor page the user clicks Get appointment. This starts the real booking.
    3. The system checks whether the profile is complete.
    4. If incomplete: Profile gate, then the 4-step profile form, then Save. After saving, the user returns automatically to the
       booking.
    5. Schedule page: choose date and time.
    6. Visit form, then Review, then Confirm.
    7. Success page with the tracking code. Next: view details, My appointments, or a new appointment.


Flow B: returning user
Same as Flow A but steps 3 and 4 are skipped: Get appointment goes straight to the Schedule page.

Flow C: manage appointments
Profile menu (or the next-appointment card on the landing hero) to Appointments table, then a row opens the Details sheet,
where the user can print or cancel (if active).

Flow D: profile
Profile menu to My profile (table). From there: Edit profile, Export PDF, Export Excel.

GLOBAL 3

Shared Behavior
City selector (header, global)
 - The header city button filters doctors everywhere. Current list: Tehran and Karaj only (expansion deferred by the owner).
   Default: Tehran.
 - The choice is stored in localStorage (key: city) and applied instantly to the Doctors list and the Doctor suggestions on the
   landing page.
 - Sample doctors exist only for Tehran and Karaj. Other cities, once added, must show an empty state, not an error.


Header search
 - Typing and pressing Enter (or the search icon) goes to /doctors?q=text. It matches doctor name and specialty name,
   limited to the selected city.
 - On mobile the search is an icon that opens a full-width search row.


Profile menu (header, top-left icon)
Item                             Behavior
My appointments                  Goes to /appointments
My profile                       Goes to /profile (if no profile yet, the page shows an empty state with a create button)
Settings                         No page yet: disabled or coming-soon hint
Log out                          Confirmation dialog. On confirm: delete everything stored about the account (saved profile, drafts and
                                 ALL appointments). Only the selected city stays, because it is a device preference. Then go to the
                                 landing page, where the hero returns to its new-user state. Nothing about the old account may be shown
                                 afterwards. There is no real account.



Profile completeness gate
 - A profile is complete when every required field of all 4 steps is filled and valid.
 - The check happens when booking starts (Get appointment on the Doctor page), never in the middle of the visit form.
   This is a deliberate decision: the user must never fill a visit form and then discover a long profile form is also needed.
 - The profile is filled once, saved in the browser, and reused for every later visit.

Form conventions (all forms)
 - Validate on blur and when pressing Next or Submit. Show friendly Persian messages under the field (for example:
   required field; national ID is not valid; mobile number must be 11 digits starting with 09).
 - On Next with errors: do not move on, scroll to and focus the first invalid field.
 - The only button that may be disabled is Continue on the Schedule page (until a time is chosen), with a one-line
   explanation under it.
 - Unsaved-changes guard: leaving a dirty form (link click or browser Back out of the flow) opens a confirmation dialog with
   Stay and Leave.

   information. (Only on these forms; not on the landing page or footer.)
 - Success and failure feedback uses a short toast.


Iran-specific validation
Field                        Rule
National ID                  10 digits after normalization. Reject all-same-digit values. Checksum: s = sum of digit[i] * (10 - i) for i = 0 to 8;
                             r = s mod 11; valid if (r < 2 and check digit = r) or (r >= 2 and check digit = 11 - r).
Mobile                       Regex ^09[0-9]{9}$ after normalization
Names                        Persian letters and spaces (allow zero-width non-joiner), 2 to 40 characters
Birth date                   Jalali date picker; not in the future; age at most 120
Height / weight              Height 50 to 250 cm; weight 2 to 300 kg; numbers only

Doctors List
Route: /doctors            (query: specialty, sort, q)
One page template that serves every specialty. Lets the user browse doctors in the selected city and open a doctor page. It
does not start booking.

Entry points
 - Landing specialty tile: /doctors?specialty=slug. Landing view-all link and header Doctors link: /doctors.
 - Header search: /doctors?q=text. Landing doctor card button is not an entry point (it opens the Doctor page).


Content, top to bottom
 1. Back button and breadcrumb: Home > Doctors (> specialty name when filtered).
 2. Page title: Doctors of the selected specialty in the selected city (or all doctors in the city).
 3. Context row: city chip with a Change link that opens the header city selector; active search chip (q) with a clear button.
 4. Filter bar: Specialty (Select with All plus 8 options) and Sort (Select: soonest available [default], highest rated, most
    reviews).
 5. Result count, for example: 3 doctors found.
 6. Doctor grid using the existing doctor card: fixed-size person icon, name, specialty, stars with Out of N reviews, Today tag
    only when applicable, button Get appointment.


Behavior
 - Filters live in the URL query so refresh and sharing keep them; changing any filter updates results instantly (no submit
   button).
 - The whole card and its button both open /doctors/:id. Hovering follows the existing card behavior.
 - City from the header always applies. Changing the city re-filters the list immediately.
 - Sort soonest: doctors with Today first, then by highest rating. No pagination needed (at most 12 doctors).


Flows
 1. User taps a specialty tile on the landing page, sees the filtered list, opens a doctor, continues to the Doctor page.
 2. User types a name in the header search, sees matches, opens one.
 3. User changes the city in the header while on the list and sees the list update in place.

 - Person icon has the same size on every card. Today tag appears only for flagged doctors.
 - Works at 360 px: filter bar stacks, cards in one column.

SITE PAGE 2

Doctor Page
Route: /doctors/:id
Full page for one doctor (not a side panel). Builds trust and is where booking starts. Reviews are at the bottom of the page.

Entry points
 - Any doctor card (landing today section, Doctors list). Button label on the card is Get appointment; it opens this page.


Content, top to bottom
1. Back button and breadcrumb: Home > Doctors > doctor name.
2. Header block: fixed-size person icon (photo if ever present), name, specialty, city, stars with Out of N reviews, Today tag
   if applicable, sample medical council number.
3. In-page anchor links: About, Practice, Reviews (scroll to sections; no tabs, so reviews are never hidden).
4. About: a short bio of two to three sentences and experience note.
5. Practice information: address, working hours, accepted insurances (list).
6. Reviews (bottom of the page): rating summary (average, total count, 5-to-1 distribution bars consistent with the doctor
   rating), then the list of sample reviews (stars, name, Jalali date, text) with a Show more button (see GLOBAL 4). Read-
   only.


Booking panel (side column on desktop, sticky bottom bar on mobile)
 - Shows the next three available days with up to four time chips each (ToggleGroup, single select) and the primary button
    Get appointment.
 - Choosing a chip is optional. If a chip is chosen, it is passed to the Schedule page and preselected there.
 - If the doctor has no free slot in the next 14 days: show a no-availability message and disable the button.


Behavior of Get appointment
1. Profile complete: go to /book/schedule?doctor=:id (plus date and time if a chip was chosen).
2. Profile incomplete: go to /book/start?doctor=:id (Profile gate).


Flows
1. From list or landing, open card, read about and reviews, pick a time chip, click Get appointment, continue per Flow A or
   B.
2. Back returns to where the user came from; on direct load the fallback is /doctors.


Edge cases and acceptance checks
 - Unknown :id shows a not-found state with a button back to the Doctors list.
 - Doctor from another city than the selected one still opens (shareable link) and shows its own city.
 - Reviews section is the last content section before the footer. Show more appends 6 reviews once, then hides.
 - Booking panel stays reachable on mobile without scrolling back up.

My Profile: Summary Table with Export
Route: /profile
A clean table view of everything in the saved profile, with Export PDF and Export Excel buttons. Persian must render
correctly in both exports. This page is the proof of the form-to-table-to-file idea.

Entry points
 - Profile menu, My profile. After saving the profile (when there is no returnTo). Edit links elsewhere.


Content, top to bottom
1.      Back button (to Landing) and breadcrumb: Home > My profile.
2.      Title, completeness status chip, and last updated date (Jalali).
3.      Action row: Edit profile (goes to /profile/edit/identity), Export PDF, Export Excel.
4.      Four section tables, each a two-column label and value table: Identity, Contact, Insurance, Medical history.
5.      Display rules: Jalali long date for birth date; gender and other choices as their Persian labels; conditions shown as a
        comma list (or chips); empty optional fields show a dash; Persian digits everywhere.


Empty state
 - No profile yet: message plus Create profile button (goes to /profile/edit/identity). Export buttons are hidden.


Export PDF
 - Content: brand name, title Patient profile, export date (Jalali), the same four tables, a short educational-sample note in the
   footer.
 - Recommended method: a print-optimized view of the same page (print stylesheet, A4 portrait, 15 mm margins, no
   header, footer or buttons, tables never split mid-row) and window.print(). Set document.title to nobat-yar-profile before
   printing so the saved file gets a clean name. The button label stays Export PDF; the user chooses Save as PDF in the
   dialog. This method renders Persian perfectly with the page font.
 - Fallback if one-click download is required: render the print view to canvas (html2canvas) and place it into a PDF
   (jsPDF). Persian is correct, but text is not selectable and the file is larger. Say so in the final notes.
 - Do not use jsPDF text drawing or pdfmake with default fonts: Persian letters come out disconnected or reversed. If direct
   text is ever required, embed the project font and test with the acceptance strings below.


Export Excel
 - Library: SheetJS (xlsx) or ExcelJS. File name: nobat-yar-profile.xlsx. One worksheet named in Persian (profile).
 - Layout: two columns (Field, Value). Each section is a bold header row followed by its rows. Header row styled and frozen.
   Column widths set; text wrapped.
 - Worksheet direction must be right-to-left (sheet view rightToLeft). Set a Persian-capable font (for example Tahoma) on
   all cells.
 - Write dates as Jalali text strings (not Excel date serials) and keep Persian digits in display values. National ID and mobile
   must be text cells so leading zeros are never dropped.


Acceptance checks
 - Open the PDF and the Excel file: joined Persian letters, correct word order, Persian digits, no empty boxes. Test strings: a
   name with a half-space, a long address-like text, a mobile starting with 09, and a Jalali date.
 - The profile is shown in the same order and wording as the form. Export buttons are keyboard accessible.
 - The page works at 360 px: tables stay readable (label above value is acceptable on mobile).

Route: /book/review
Last step before creating the appointment. Shows everything entered and lets the user fix any part without losing the rest.

Content, top to bottom
1. Back button (to Visit form), breadcrumb, progress indicator.
2. Three summary cards: Appointment (doctor, specialty, city, date, time), Visit (all visit answers), Profile (compact read-
   only summary of the saved profile).

   /profile/edit/identity?returnTo=/book/review.

Behavior of Confirm
1.   Disable the button immediately to prevent double submission.
2.   Create the appointment: unique 6-digit code, status active, copy of the visit values, snapshot of the profile, createdAt.
3.   Append it to the appointments list in localStorage and clear bookingDraft.
4.   Navigate with replace to /book/done?code=XXXXXX so browser Back never returns here or re-submits.


Edge cases and acceptance checks
 - Missing draft data: redirect to the first incomplete step.
 - Returning from any Edit link lands back on this page with all values intact.
 - The code is unique across stored appointments.

Global Acceptance Checklist and Deferred Items
Global checks
 - Every page and every step has a visible Back button; data survives Back and refresh where specified.
 - No checkbox exists anywhere; ToggleGroup multiple is used for conditions.
 - Persian digits and Jalali dates display everywhere; Latin digits and ISO dates are stored.
 - Profile is checked when booking starts, never in the middle of the visit form.
 - Log out clears profile, drafts and all appointments; afterwards the hero shows the new-user state and My appointments is
   empty.
 - Doctor cards open the Doctor page; only the Doctor page starts booking.
 - Exports (profile PDF and Excel) and print (appointment sheet) pass the Persian rendering checks.
 - ?seed=1 populates demo data; ?seed=0 clears it. Every page is reviewed at desktop width and at 360 px.
 - No console errors. No new colors, fonts or card shapes outside the existing design system.

 - Complete province and city list and selector (only Tehran and Karaj for now).
 - Settings page. All-specialties page. Real login and backend. Payments and notifications. User-written reviews.
 - Rescheduling an appointment (only cancel exists).
